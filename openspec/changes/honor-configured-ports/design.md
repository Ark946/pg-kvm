# Design

## Context

三个服务端口由 `WebRtcSessionManagerImpl` 持久化并可配置。`/api/status` 已由网页端每 2 秒轮询，但响应中没有端口信息。`frontend/src/App.vue` 在模块加载时把 `WS_URL` 写死为 `ws://<host>:3000`，输入为 `:3001`，因此端口配置对网页端无效。

约束：网页端与 HTTP 服务同源；信令与输入是独立的 WebSocket 端口；修改端口后服务会重启。

## Goals / Non-Goals

**Goals:**

- 网页端使用设备当前生效的信令与输入端口。
- 状态不可用时给出明确错误，不静默连接到旧端口。
- 保持 `/api/status` 既有字段兼容。

**Non-Goals:**

- 在页面不刷新的情况下自动迁移已建立的连接。
- 增加 mDNS/服务发现或 HTTPS。
- 把 HTTP 端口用于 WebSocket 连接。

## Decisions

1. **在 `GET /api/status` 中增加 `ports` 对象**（`http`、`signaling`、`relay`），而不是新增 `/api/config`。
   - 理由：网页端已经轮询该接口，复用可减少一次请求和一套错误处理；新增对象字段向后兼容。
   - 备选：独立 `/api/config`——职责更单一，但增加端点、文档和前端加载顺序；当前规模不值得。
   - 备选：构建时注入配置——端口是运行时配置，构建期无法得知。

2. **在开始拉流时读取最新状态并动态拼接 WS URL**，移除模块级常量。
   - 理由：端口可能在上次轮询后改变；开始拉流是唯一需要端口的时刻，此时拉取一次最可靠。
   - 备选：依赖 2 秒轮询缓存——可能使用旧端口，产生难以诊断的连接失败。

3. **端口缺失或状态不可用时拒绝连接并显示错误**，不回退 3000/3001。
   - 理由：契约要求 MUST 使用设备当前端口；回退会掩盖配置错误并连接到错误服务。
   - 备选：回退默认端口——在旧版本/异常状态下能工作，但违反契约。

4. **修改端口后要求用户重新加载页面**；网页端不监听端口变化并迁移连接。
   - 理由：与 `web-console` 契约一致；迁移活动连接需要重建 PeerConnection 和输入会话，复杂度高且收益低。

5. **主机名取自 `window.location.hostname`**，HTTP 同源访问不变。
   - 理由：网页端本身就是从设备 HTTP 服务加载的，主机名可靠。

## Risks / Trade-offs

- [状态请求失败导致无法开始拉流] → 明确展示错误并提供重试（重新点击开始），比连接错误端口更可诊断。
- [端口在页面打开后、开始拉流前被修改] → 开始前重新拉取状态，使用新端口。
- [`/api/status` 增加字段被旧客户端忽略] → 附加字段向后兼容，无破坏性。
- [用户修改端口后未刷新页面，旧连接仍工作] → 允许；spec 只要求重新加载后使用新端口。

## Migration Plan

无持久化或协议迁移。发布后网页端自动从 `/api/status` 取端口；旧版本设备若缺少字段，网页端按“不可用”处理并提示。
